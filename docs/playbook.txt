1. How an AI coding agent should use this document
 Execute phases in order. Do not skip acceptance criteria.
 Keep the application deployable after every phase; commit working increments.
 Use a modular monolith first. Do not introduce microservices until load, organizational boundaries, or 
independent deployment needs justify them.
 All stock-changing operations must be transactional and auditable.
 Do not store plaintext passwords, secrets, or production credentials in source control.
 Prefer database correctness over cache correctness: PostgreSQL is the system of record; Redis is disposable 
acceleration state.

4. Non-functional requirements
 Correctness: no negative stock; no expired batch sale; duplicate concurrent sale must not oversell.
 Atomicity: purchase, sale, cancellation and stock adjustments either fully commit or fully roll back.
 Auditability: every stock mutation creates a stock_movement record.
 Security: authenticated APIs, role-based authorization, password hashing, input validation and least 
privilege.
 Performance: indexed high-frequency queries; cache only suitable reads; paginate large tables.
 Operability: health checks, metrics, logs, tracing IDs, backups and documented recovery.
 Scalability: stateless API instances; shared PostgreSQL/Redis/RabbitMQ; horizontal scale when needed.

@Transactional
createPurchase(request, userId):
  validate supplier is active
  insert purchase header
  total = 0
  for item in request.items:
    validate medicine active
    batch = find batch by (medicineId, batchNumber)
    if missing: create with expiry/prices/currentQuantity=0
    else: verify expiry/pricing policy for existing batch
    insert purchase_item
    increment batch.currentQuantity by item.quantity

Repository query concept:
SELECT *
FROM batches
WHERE medicine_id = :medicineId
  AND current_quantity > 0
  AND status = 'ACTIVE'
  AND expiry_date >= CURRENT_DATE
ORDER BY expiry_date ASC, id ASC
FOR UPDATE;
@Transactional
createSale(request, userId):
  insert sale header (or reserve invoice id inside transaction)
  for requested medicine + quantity:
    lock eligible batches using FEFO query
    if sum(available) < requested quantity: throw InsufficientStock -> rollback
    remaining = requested quantity
    for batch in locked batches until remaining == 0:
      take = min(batch.currentQuantity, remaining)
      insert sale_item(batchId, take, sellingPrice)
      decrement batch.currentQuantity
      insert stock_movement(SALE_OUT, take, SALE, saleId)
      remaining -= take
  calculate sale total from persisted sale_items
  commit
Why FOR UPDATE:
Two cashiers selling the same last units must serialize on the affected batch rows.
The second transaction sees the updated quantity after the first commits.
12. Critical transaction 3 - Cancel Sale
@Transactional
cancelSale(saleId, reason, userId):
  load sale FOR UPDATE
  require status == COMPLETED
  load sale_items
  lock all referenced batches in deterministic id order
  for item:
    increment batch.currentQuantity by item.quantity
    insert stock_movement(SALE_CANCEL_RESTORE, item.quantity, SALE, saleId)
  set sale.status=CANCELLED
  set cancellation_reason, cancelled_at, cancelled_by
Idempotency rule:
A second cancellation request must not restore stock twice. Return current cancelled state or 409.
13. Inventory query rules
Current stock by medicine:
SUM(batch.current_quantity) for active/non-expired batches, grouped by medicine.
Low stock:
SUM(current_quantity) <= medicine.low_stock_threshold.
Out of stock:
SUM(current_quantity) = 0.
Near expiry:
expiry_date BETWEEN CURRENT_DATE AND CURRENT_DATE + :days.
Expired:
expiry_date < CURRENT_DATE AND current_quantity > 0.

14. Caching strategy
Add Redis after correctness and baseline performance are working. Cache reads that are safe to be temporarily 
stale; never use Redis as the authoritative stock count.
Data Cache? TTL / invalidation
Medicine master by id Yes 5-30 min; evict on medicine update.
Supplier by id Yes 5-30 min; evict on update.
Dashboard summary Yes, optional 15-60 sec; short TTL.
Inventory available stock Usually no at first
Stock is highly mutable; database query + 
indexes first. If cached later, use short 
TTL and explicit invalidation.
Authentication/session Optional Depends on auth model.
Rate-limit counters Yes Redis atomic INCR / token-bucket 
implementation.
Cache-aside pattern:
1. Service checks Redis.
2. Cache miss -> load PostgreSQL.
3. Put value with TTL.
4. On master-data mutation -> evict corresponding cache key.
5. If Redis is down -> continue from PostgreSQL where possible.
15. Messaging and background jobs
RabbitMQ should be used only for work that does not need to complete before the user receives the core 
transaction result.
 Low-stock/expiry alert notifications
 Daily report generation
 Email delivery
 Audit/export jobs
 Scheduled expiry-status maintenance
Transactional caution:
Do not publish a message that claims a sale completed before the database transaction commits.
For stronger guarantees, add an Outbox table in a later hardening phase:
DB transaction -> business rows + outbox event -> commit -> publisher sends outbox -> marks sent.
16. Security
 Use Spring Security. Hash passwords with BCrypt/Argon2; never encrypt-and-recover passwords.
 Roles: OWNER and CASHIER. Restrict user/admin settings and destructive actions to OWNER.
 Validate request DTOs with Jakarta Validation and enforce DB constraints too.
 Use HTTPS outside local development; secure cookies if cookie-based auth.
 Protect against CSRF according to auth model; configure CORS to known frontend origins.
 Never log passwords, tokens, full card/payment data or secrets.
 Use environment variables/secret manager for DB credentials and signing secrets.
 Implement rate limits on login and expensive endpoints.

22. Scaling path
Do not start with Kubernetes or microservices. Scale only after measurement shows a need.
1. Stage 1 - Single Spring Boot instance + PostgreSQL. Redis/RabbitMQ optional but available via Compose.
2. Stage 2 - Make API stateless, run multiple instances behind a reverse proxy/load balancer. Shared 
PostgreSQL/Redis/RabbitMQ.
3. Stage 3 - Tune DB pool, indexes and slow queries; introduce read replicas only for safe read workloads if 
needed.
4. Stage 4 - Separate worker processes for async jobs; scale workers based on queue depth.
5. Stage 5 - Only then consider Kubernetes, managed services, partitioning, or service extraction.
Scaling principle:
HTTP/API instances can scale horizontally because business state is externalized.
Stock correctness still depends on PostgreSQL transactions/locks, not on which API instance receives 
a request.
23. Production hardening checklist
 Database backups: automated daily backup + point-in-time recovery where available; test restore.
 Migrations: Flyway in deployment pipeline; backup before risky migration; backwards-compatible rollout 
for zero-downtime changes.
 Connection pools: HikariCP sane max sizes; do not overwhelm PostgreSQL by multiplying pods x pool size.
 Indexes monitored using query plans and slow-query logs, not guessed indiscriminately.
 Time zones: store timestamps in UTC/TIMESTAMPTZ, display local time in UI.
 Money: NUMERIC/BigDecimal; never float/double for currency.
 Pagination limits and maximum request sizes.
 Retries only for transient/idempotent operations; exponential backoff with jitter.
 Circuit breaking for external notification providers, not for local database correctness.
 Graceful shutdown and readiness/liveness probes.
 Secure headers, dependency/security scanning, container non-root user.
 Backup and restore runbook; incident and rollback runbooks.

26. Acceptance scenarios
 Create a new medicine master; it appears in the medicine table and is editable.
 Record a purchase with 3 medicines; all batches and movements appear and inventory increases.
 A purchase fails on line 2; line 1 stock must not remain increased.
 Sell 8 units when earliest batch has 5 and next batch has 20; sale creates two sale_items (5 + 3).
 Try to sell an expired batch; it is never selected.
 Two cashiers compete for the last unit; only one sale consumes it.
 Cancel a sale; exact consumed batches are restored once, not twice.
 Low-stock and near-expiry views reflect database state.
 Redis outage does not corrupt inventory; master reads fall back to DB where designed.
 RabbitMQ outage does not turn a committed sale into a failed sale; notification can retry later.
 Restart application/containers; PostgreSQL data persists.
 Run E2E journey from purchase to sale to cancellation successfully.

28. Definition of a ready V1 application
 Fresh clone can start infrastructure and application using documented commands.
 Owner can log in; medicine/supplier masters work.
 Purchase increases batch stock and records audit movements atomically.
 Inventory views are correct.
 Sale uses FEFO, prevents overselling under concurrency, and records exact batches.
 Sale cancellation restores exact stock once.
 Dashboard/reports return correct summaries.
 Health/metrics/logging are usable.
 Core integration, concurrency and E2E tests pass.
 No production secrets are committed; configuration is environment-driven.

prescriptions, pharmacy regulatory workflows, purchase returns, customer returns, GST invoice specialization, 
payment reconciliation, barcode scanner integration, supplier price intelligence, demand forecasting, SaaS 
tenancy, billing/subscriptions, mobile app, advanced warehouse transfers.
